modules/mcp_server: task090 (2c-9) step1 - the failure answer's data payload reaches the call line

TASK-090 item A. The last declared hole of the TASK-089 traceability model was
that a failed tools/call kept only `error_code` + a 512 byte `error_message`; the
`data` the tool layer attaches (`suggestion`, `parse_error`) never reached the
trace, although it is the half a caller acts on.

* mcp_trace.h/.cpp: `Record` gains `error_data_json` / `error_data_bytes`; the
  call line emits the field (with `_bytes` / `_truncated`) for every failed
  tools/call, empty when the tool attached nothing - so "this build records it"
  and "this trace predates the field" stay distinguishable. Same canonical
  JSON::stringify and same `max_args_bytes` bound as the success half.
* mcp_jsonrpc.cpp: `_record_error_data()` fills it in the immediate tool-error
  branch and in the deferred-refusal branch.
* mcp_http_server.cpp: a deferred completion writes it from
  `completion.error.data` by the same rule.
* scripts/mcp_trace_ledger.py: `error_data` / `error_data_evidence` /
  `error_flags` per row, `error_data` added to the reconstructible FACTS, and a
  "failure payloads" section in the text report.
* docs/reports/MCP-TRACEABILITY.md: §2.1 field table, §3.1 facts, §3.2 gap
  status (closed) and §5 updated.

Measured live in the round-8 session: three editor failures and three game
failures carry their `suggestion` / `parse_error` on the line; the ledger prints
them verbatim.
