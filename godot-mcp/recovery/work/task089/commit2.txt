modules/mcp_server: task089 (2c-8) step2 - the round-7 test loop: three defects fixed, the trace now carries the tool's own answer

The round-7 session drove a real mini game project (H:\rebuild\projects\mcpplay:
one scene, one script, a Theme resource, a text resource, project.godot) over
both endpoints with --mcp-trace --mcp-capture=every_call: 30 calls on the editor
(9888), 15 on the game (9889), every tool family with at least one call that
must take effect and one that must not or must be refused.

Three defects, each with a measured root cause:

F1 running_game_execute_gdscript answered every genuine parse failure as
   "Parameter 'code' does not compile: Parse error". The engine's own diagnostic
   ("Function get_node() not found in base self.", with the line) stayed on
   stderr. Root cause: this group carried its own byte-identical copy of
   build_execute_gdscript_source and called the bare Script::reload(), while
   editor_execute_gdscript already used reload_gdscript_capturing. The game tool
   now uses the module's one builder and the module's one capture, and fills
   data.parse_error exactly as the editor tool does.

F2 the call line carried result_bytes and nothing else, so a successful
   running_game_assert_node_state that answered passed:false was
   indistinguishable from one that passed. Record gains result_json /
   result_json_bytes; _build_line emits them (bounded like args); the ledger
   derives result_flags (assertion_failed / created_conflict /
   result_unparseable) and prints a flags column.

F3 project_create_script answered {"created": true, "existed_before": true} for
   the same file written twice - one response contradicting itself. The two
   sibling text writers already answer created = !existed; this group now does
   too. A doctest pins it (module suite 147 -> 148 cases).

Recorded, not changed: the game executor cannot reach the running scene at all
(self is a bare RefCounted), which is a design question, not a single root cause;
and tool_helpers.h declares two helpers twice (once outside namespace MCPTools),
which is an ambiguous-call hazard worked around with MCPTools:: qualification.

Re-running the same call set gives an identical verdict distribution on both
endpoints (work/task089/compare_ledgers.py) - the fixes change what the log can
prove, not what the tools do - and the after-run ledger surfaces the three
assertion_failed responses the before-run trace could not express.

registered in REBUILT-2C-MANIFEST.md section 2c-8 (H-5, H-6).
