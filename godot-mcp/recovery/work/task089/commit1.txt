modules/mcp_server: task089 (2c-8) step1 - the call line carries the file-side half of "did this call do anything"

The traceability model had exactly one declared gap (MCP-TRACEABILITY.md 3.2):
a call line said nothing about the files the call wrote. This is the recorder
that closes it, and it is opened in one place rather than per tool.

* mcp_file_effects.{h,cpp} (new): a per-call buffer and the MutationScope a
  mutating primitive opens around itself. One row per destination: absolute
  path, kind (write/delete/mkdir), sha256 + bytes before and after, changed,
  and - for a small text destination - a bounded head/tail line difference.
  Large files are never read, only hashed; every recorded line is clipped.
* mcp_jsonrpc.cpp: the recorder is opened around the one place a tool is really
  invoked, and only when the request is traceable. A deferred tool names itself
  not_tracked_deferred instead of looking like "no mutation".
* mcp_trace.{h,cpp}: Record carries the rows and the status; _build_line emits
  them on the call line, at the same level as id/method/tool.
* tool_helpers.cpp: publish_file_atomically (the module's single publish
  primitive) plus the one section arm that bypasses it plus the one mkdir.
  The four sites that write without the primitive (a delete, the C# build
  record, the bridge-file removal, the two cross-scene rollbacks) open the
  same scope.
* mcp_trace_ledger.py: file_effect is read off the line; ok_file_effect_observed
  is the file-side "it happened"; file_effect joins the facts_complete set.
* four doctests (module suite 143 -> 147 cases, all green).

All written text is wrapped in [REBUILT-2C low-confidence: verify] and
registered in REBUILT-2C-MANIFEST.md section 2c-8 (H-1..H-4).
