modules/mcp_server: task103 (X-1) - a GDScript body that compiles and then fails while it runs is a structured refusal now (-32000 + data.script_error + data.suggestion) instead of an ok with a null result, and a successful body that returned no value carries a note, so "ok" can no longer be read as "the script ran"

The defect (TASK-102 X-1, runs/match3/m3-task102-r1/g115-runtime-overlay): the body
called main.addChild(c) - the C# spelling of the method - on a C# Node2D. GDScript
compiled it, the VM aborted the frame at that line, and Callable::callp answered
CALL_OK with the return type's default, so the tool answered ok +
{"result":null,"result_type":"Nil"} with no error code, no message and no suggestion
while the engine's stderr carried the whole SCRIPT ERROR line. The cost was measured:
the next frame was byte-identical and the scene tree had no ProbeOverlay, so the ok
answer was the only thing pointing the wrong way - and it pointed the wrong way.

The route is the engine's own error handler, the same hook the parse capture already
uses: GDScriptFunction::call() reports an aborted frame through
_err_print_error(err_func, err_file, err_line, err_text, false, ERR_HANDLER_SCRIPT)
(modules/gdscript/gdscript_vm.cpp:3988, inside #ifdef DEBUG_ENABLED, which every
target=editor build these gates run defines - SConstruct:550/566-569; the boundary
that leaves, a release template, is stated in the tool rather than assumed). The
window is exactly one Callable::callp, so every ERR_HANDLER_SCRIPT emitted between
the install and the removal happened because of this call, and ERR_HANDLER_SCRIPT
(not ERR_HANDLER_ERROR) is what keeps a body's own deliberate push_error() out of
the verdict.

- code: -32000 (tool_state), never -32602 (the body compiled: its syntax is fine)
  and never -32603 (this module is not the thing that failed). data.script_error
  carries the engine's own message, the line of 'code', the generated line, the
  script path, the blamed GDScript function, the error count and every message;
  data.suggestion says what to do about it. The column is reported absent, because
  the engine hands a handler a line and never a column.
- the generated script's identity is reconstructed the way GDScript makes it
  (`gdscript://<instance id>.gd`, gdscript.cpp:1337) instead of read from
  Script::get_path(): that is Resource::get_path(), which answers the path cache and
  is empty for a script that was never loaded - measured, the runtime error named
  gdscript://-9223371484028730203.gd while get_path() answered "". The answer
  carries both strings, so the comparison is auditable.
- the success path: a null/Nil result carries a note, because a null result is also
  what a body with no `return`, and a body whose statements were all no-ops, answer.
- the tool's description and its C++ registration literal are regenerated through
  the generator's append-only override (`execute_game_script`); the contract's six
  shape quantities are unchanged (count 177, added_count 6, generator_version
  1.22.0, editor-visible 154, game-visible 73, and idempotent: two consecutive
  generator runs answer sha256 bd68e80472c8e15d674c45bf5816ee708ea08cf71f209a0e0114373d6067b640).
- doctests: a new case pins the three situations apart (parse failure -32602; runtime
  error -32000 with data.script_error and its line mapping; success with a value and
  success without one, the latter carrying the note) plus the push_error control that
  must NOT become a refusal, and the TASK-090 mount case now asserts the structured
  refusal on its own failure path. Module case count 156 -> 157.
