## 1. 目标（三块，缺一不可）

### A. 真实输入通路（OS 级）验证 —— 回答"真人按键到底有没有反应"
1. **先判定本机是否具备"把键送到窗口"的条件**（只读探测，逐条留原始输出）：
   * 显示器/会话状态（`nvidia-smi` 的 `display_active`、`GetSystemMetrics` 的显示器数量/分辨率、
     `GetForegroundWindow`、会话是否为交互式桌面）；
   * 能否把某个窗口**置为前台**（对游戏窗口尝试 `SetForegroundWindow`，记录返回与前后 `GetForegroundWindow`）；
   * `SendInput`/`keybd_event` 是否成功返回（记录 sent 计数与 `GetLastError`）。
2. **真实键实测**：启动一款**发布版 exe**（建议 `pong`，可另加 1–2 款），把窗口置前台后，
   用 **Win32 `SendInput`** 发送该游戏**已声明的按键**（按键名与键码取自 `project.godot` 的 InputMap），
   同时用 MCP 端点采集：**状态快照（sha256）** + **整窗帧（sha256、像素差）** + `frame_count`。
   * 判据：按键前后是否出现**可归因的状态或像素变化**；**记录焦点状态与是否"什么都没发生"**。
3. **对照臂**：同一款游戏用门的 **MCP 合成注入**（`Input.parse_input_event`）跑同一动作，
   给出**两条通路的结果对照表**（真实键 vs 合成注入）。
4. **结论必须三选一并给证据**：
   * ①真实键有效 → 记录（并给出焦点/送达证据）；
   * ②真实键无效、但本机**无法提供前台焦点/活动显示** → 明确写成**本机环境限制**，
     并说明**该限制下我们无法用真实键验收**（这是诚实的边界，不是游戏缺陷）；
   * ③真实键无效、而**焦点与送达都成立** → **这是真缺陷（游戏侧输入未被 OS 事件驱动）**，
     按既有流程修（若涉及引擎模块则两变体重建 + 十道门 + `accept_m1` + push）。
5. **无论哪种结论**，都要给出**"在没有真实键能力时，替代证据是什么"**：例如把注入点放在
   **DisplayServer 边界之上**（若引擎暴露了可注入 OS 事件的接口），或**由人/我读图复核**，并写明其强度上限。

### B. 取证对应关系核对 —— 回答"游戏记录和截图功能是否对应上了"
对**至少两款游戏**（含 pong）产出一张**逐步对应表**，每一步都要有可复核的原始证据：
* 步骤序号 → **注入的调用**（`seq`、工具名、参数）→ **同一时刻的状态快照**（字段值 + sha256）→
  **该次采集的帧**（帧 id、文件路径、sha256、与前一帧的像素差）→ 时间戳（`ts_ms`/`frame_count`）；
* **必须证明取证与被注入输入属于同一实例**：游戏进程 pid、MCP 端口、trace 文件名、
  引擎版本串（`--version`）四处对齐；若发现帧来自编辑器进程/内嵌小窗/另一个进程 → **判 FAIL 并点名**；
* 明确写出**采集的视口**（整窗？游戏视口？裁剪？）与**分辨率**，并核对是否等于工程声明值。

### C. 强制读图（硬判据）—— 回答"子代理有去读取图片验证操作轨迹正确吗"
* 对 A/B 产生的帧与 filmstrip，**必须用 `read_image` 逐帧实际查看**（不是只算像素差），
