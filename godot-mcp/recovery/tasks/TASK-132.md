## 1. 目标

做一个**模型玩家回路**（`tools/playtest_player.py`），并对**至少 3 款游戏**产出结论与 demo 产物：

### 1.1 回路（每一步都必须落证据）
1. **采集**：从**游戏进程**（game 端点、整窗）取一帧 800×600 截图（记 sha256、`frame_count`、时间戳）。
2. **模型出操作**：把该帧作为 **1 张图 + 1 个 `choice` 问题**发给 Jev（8080），
   `criteria` = **该游戏声明的动作集**（取自 `playability_controls.json` / 工程 `project.godot` 的 InputMap，
   **写清你如何取到**）；记录返回的 `choice`、`probabilities`、`confidence`、`usage`。
3. **注入**：把该动作注入游戏（沿用门的忠实通道 `Input.parse_input_event`；若 TASK-131 证明真实 OS 键可用，
   **至少对 1 款**再用 Win32 `SendInput` 跑一条对照），记录所用通道与注入 `seq`。
4. **接受判定（ack）**：给出"游戏确实接受了这个输入"的证据——例如注入时刻该动作的 `Input.is_action_pressed`
   为真，且/或游戏侧状态/日志显示该动作生效；**必须指名用了哪条证据**。
5. **变化判定（change）**：注入后取后续帧（例如 10–30 帧内），给**前后帧像素差**与**声明的玩法可观测**
   （位置/速度/得分/棋盘推进）的变化；**与"注入前的等长无输入对照窗口"比较**，排除"本来就在动"的误判。
6. **逐步记录**到 `runs/model-player/<game>/steps.jsonl`：
   `{step, frame_before_sha, frame_after_sha, pixel_diff, control_diff, state_before_sha, state_after_sha,
     action, probs, confidence, channel, ack_evidence, changed_bool}`。

### 1.2 判定规则（**严格照用户口径**）
* **FAIL（用户的"问题"）**：`模型出了操作` ∧ `游戏接受了输入（ack 成立）` ∧ **`画面没有动态变化`**。
* **PASS**：连续 **≥8 步**里"ack 成立 ∧ 视口出现动态变化"的比例 **≥ 75%**，**且**
  **子代理读图判定这些前后变化符合游戏逻辑**（见 §1.3）。
* **INCONCLUSIVE（证据不足）**：模型连续给出**同一动作**、或动作集与游戏无关、或模型拒答/abstain，
  导致无法判断"是否接受/是否变化"→ **如实标为证据不足**，并说明缺什么。
* **其他判据（P1–P7）只报"代码能跑"**（能起、能渲染、能采帧、能注入），**不得**再用它们下"可玩"结论。

### 1.3 强制读图（子代理本人必须做）
* 对每款的**每一步**：用 `read_image` 实际查看 `frame_before` 与 `frame_after`，写下：
  **看到了什么 → 与上一帧比变了什么 → 这个变化与该步操作是否合理**（例如"按上键后挡板确实上移"）。
* 产出**逐帧描述表**；**不能读图就显式声明**，**不得**用像素差数字冒充看图。
* 判"符合游戏逻辑"时要**写出你的推理依据**（例如蛇向右移动后食物消失、分数 +1）。

### 1.4 demo 布局产物（照 Jev 仓库 demo）
* 每款生成 **`runs/model-player/<game>/demo.png`**（或 `demo.html`）：**左=游戏帧序列**（至少关键 6–10 步），
  **右=该步 Jev 输出的按键/操作示意**（动作名 + 概率；与左对齐）。**一图可读懂"模型在玩什么"**。
* 同时保留 filmstrip（沿用门的既有格式），便于人眼复核。
