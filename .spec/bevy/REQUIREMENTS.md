## 1. 目标（要达成什么，第一性）

让 hof-rs 在**全新空白工程**上，用 **Bevy 0.19.1** 作为游戏开发适配器，由三角色流水线**真实产出一个可玩的小游戏**，
并且该游戏的**关键行为在游戏进程内被语义工具观测并证实**——而不是由模型拼装脚本自证。

成功 = 判据 (1)..(5) 全部满足（§6）。

## 2. 非目标（本次明确不做）

1. **不删除 Godot 侧**：Godot 路径保留为 legacy、可编译、不再演进（D296 用户取舍）。
2. **不把像素/截图作为判据**（用户决定）：证据一律来自 ECS 语义；`game.screenshot` 不在验收口径内。
3. **不做名字映射**：不把旧 177 条 Godot 工具名映射到 BRP 的 23 个动词（SPIKE-1 明确警告：语义面完全不同）。
4. **不改 `godot-mcp/**`**、不改 Godot 时期冻结的 `PRD-mario.md`（其作为历史工件保留）。
5. 本次不做 headless/无 GPU、跨平台与 release 暖增量的能力承诺（SPIKE-1 未测，列为未验证项）。

## 4. 硬约束（不可违反）

1. **冻结工件**：新 Bevy PRD 逐字节冻结（另设 sha256）；**BRP-MCP 工具清单逐字冻结**（含工具名、参数 schema、返回 schema）。
2. **可反射语义契约冻结**：游戏暴露的语义类型**全限定类型路径（含 crate 名）就是契约**，必须冻结；其变更等同契约变更。
3. **适配器 trait 化**：新增 Bevy 适配器；Godot 适配器保留且仍可编译（`godot-mcp/**` 不动）。
4. **构建契约**：适配器契约显式声明——**共享持久 target 目录**、**冻结 feature 集**（feature 漂移会使暖增量从约 18 s 变约 236 s）、
   **冻结 `Cargo.lock`**、**轮 0 预热**；预算上界：**冷 ≤600 s / 暖 ≤90 s / 单轮 ≤300 s / 端点等待轮询超时 30 s**。
5. **端点与协议**：固定 **15702（主世界）**，不使用 15703；HTTP/1.1 JSON-RPC 2.0；**HTTP 恒 200、错误在 body**，故适配器**必须解析 body 判成败**；
   无认证、无 TLS（仅回环，不得暴露到非回环接口）。
6. **`runs/**` 绝对零写入**（除该轮自身目录）；`PRD-mario.md`、`DECISIONS.md`、引擎树、`godot-mcp/**` 不动。
7. **验收通过后才 push**（闸门已武装；verdict 非 `pass` 的批次不得推送）。
8. **每批改动由另一批全新子代理独立验收**。

## 5. 边界与假设

**边界**：
- 适配器只负责：构建/启动游戏、经 MCP→BRP 注入输入与读取语义状态、收集证据、判定本批是否可交付；
- 游戏如何实现玩法属 **Developer 角色**的产出，不在适配器职责内；但**游戏必须满足可观测契约**（§7）。

**假设（默认成立，但需你确认）**：
- A1. 目标游戏为**横版跳跃类**（沿用 Godot 时期 `PRD-mario.md` 的**玩法语义**，但**重新撰写为 Bevy PRD**）。
- A2. 运行环境有 GPU、能开窗口（SPIKE-1 未测 headless ⇒ 本次不作承诺）。
- A3. 角色可用文件系统 + cargo 编写游戏（Bevy 无编辑器，编写期工具面就是文件系统与构建）。
- A4. 单轮预算按 §4.4，允许首轮较长（冷构建）。

## 6. 验收标准（判据 E1..E6，Bevy 口径）

| 编号 | 判据 | 证据来源 |
|---|---|---|
| **E1** | `hoh init` 全新空白工程后，`hoh run` 由三角色流水线**产出真实工程增量**（`A_1 ≠ A_0`，且增量确为游戏工程文件） | 前后目录哈希树 + 角色轨迹 |
| **E2** | 产出的游戏**能构建并启动**，且门（artifact gate）为绿：无编辑器/编译错误类项目缺陷；失败必须是**真实项目缺陷**而非基础设施噪声 | 构建日志 + 门 reasons + 启动到端点就绪的实测耗时 |
| **E3** | **四类关键行为在游戏进程内经语义工具观测证实**：①注入输入后玩家位移改变 ②金币计数发生 0→N 跳变 ③胜利标记 false→true ④**跳跃呈现真实上升与下降**（上升步数 > 0、峰值高于地面、且有下降步） | MCP→BRP 调用与返回的原始 JSON（含时间戳、调用序号、参数与返回值） |
| **E4** | **可复现**：同一条命令在干净环境重跑得到同类结果；`runs/**` 留全证据（轨迹、原始调用、门读数、哈希） | 两轮并列证据 + 清理前后目录状态 |
| **E5** | Tester **未修改**冻结的候选快照（含经排除目录的写入，必须被检测并拒绝） | 快照哈希前后一致 + `qa_*` 警告缺失/出现 |
| **E6** | Tester 的裁决**诚实**：未观测到的一律不得报为已验证；未满足项必须显式列出 | `qa_status`、逐项 verified id 与原始观测的对应关系 |

**E3 的口径补充（防假证据）**：
- 证据必须来自**语义工具调用**（MCP→BRP），**不得**来自模型自行编写的观测脚本；
- 跳跃必须**同时**有上升步与下降步；**单调下落不算**（Godot 时期该判据正是这样红的）；
- 注入输入必须**电平触发**（边沿由游戏自清）；事件类型必须**带命名字段**（SPIKE-1：单元结构体事件经 `observe+watch` 收不到帧）。

## 7. 游戏必须满足的可观测契约（PRD 未来章节的输入）

1. `bevy = { features = ["bevy_remote"] }` + `RemotePlugin::default()` + `RemoteHttpPlugin::default()`（**dev 构建**）。
2. 对下列语义面加 `#[reflect(Component/Resource)]` + `register_type`，并**冻结其全限定类型路径**：
   玩家标记、`Grounded`（或等价的可读接地状态）、金币计数资源、胜利位资源、**注入意图事件/资源**。
3. 关键状态**不得**藏在不可反射的引擎资源里（SPIKE-1 实测 `bevy_time::time::Time` 读不到）。
4. 注入面为**电平触发**的持续量；**边沿由游戏自清**（实测：每帧清零时 0.4 s 只走 2 px，改电平后走 92 px）。
5. 位移读取用**点号路径** `translation.x`；**不得**用 JSON 数组下标 `translation[0]`（实测报错）。

## 8. 复盘：假设清单与待确认问题

**你可能默认成立、但我必须点出的假设**：
- A1（玩法沿用横版跳跃语义）——若不成立，PRD 与 E3 的四类行为需重定义；
- A2（有 GPU 能开窗口）——SPIKE-1 未测 headless，若我们要在无 GPU 环境跑，需另做 spike；
- "四类行为"是否就是**唯一的** E3 口径（是否还要加"接地"作为可读语义，SPIKE-1 表明它必须由游戏暴露，不能从像素推断）。

**人们在这类问题上最常犯的一个错误**：把**新引擎的工具面**当成**旧引擎工具面的改名**，
于是把旧契约的形状（大而全的 177 条、编辑器语义）硬套到新引擎（23 条、ECS 语义），
结果契约臃肿且与真实能力错位。SPIKE-1 已明确警告这一点——我们的对策是**两层工具面：通用层 1:1 pass-through + 语义层 <10 条绑定冻结契约**。

**待你确认的三个问题**：
1. **玩法语义**是否沿用横版跳跃（A1）？若是，我将据此撰写 Bevy 专用 PRD 并冻结。
2. **E3 是否要把"接地"（Grounded）纳入**为可读语义判据？（它必须由游戏暴露，BRP 无法从像素推断。）
3. **headless/无 GPU 环境**是否需要支持？（需要则先补一个 spike，影响 CI 可行性。）

## 10. SPIKE-2 裁决落地（headless / 无 GPU）

依据 `.spec/bevy/SPIKE-2-REPORT.md`（672 行，全部为仓外实测，仓库 tracked 文件零改动）。**以下条款取代 §4.5、§5-A2 与 §4.4 的预算数字。**

1. **承诺 headless，现在就做**，形态为**同一二进制 + 运行时开关**（约 20 行 `main()` 分支，依赖行不变）：
   开关关闭时开 1 个真窗口；开启时 **0 窗口、无渲染世界**。**每轮与 CI 一律用 headless**——
   实测窗口模式在本机只有 **4.0 FPS**（`WinitSettings::continuous()` 无效），跳跃弧线仅采到 6 点（rise=0/fall=2），
   而**同一渲染世界的无窗口模式为 60.3 FPS**；即"有 GPU 能开窗口"**不等于**"能观测"。
2. **必加 `ScheduleRunnerPlugin`**：不给则应用一帧后以 rc=0 退出、**端点从未绑定**（C7 实测）。
3. **GPU 无关性**：`RenderCreation::Automatic(WgpuSettings{ backends: None })` 下**不存在渲染世界**（源码面：不加 `ExtractPlugin`）。
   受控毒化实验（空后端集）证明 C1/C2 panic 而 C3/C4 照常运行 ⇒ **GPU 无关是被证明的**。
4. **端点规则（取代 §4.5）**：**15702 恒存在、恒 23 方法 ⇒ 适配器只依赖 15702**；
   **15703 当且仅当存在渲染世界时存在，适配器不得依赖它**（不得改为条件式，只需按此措辞描述）。
5. **A2 删除，替换为**：适配器**必须能在无窗口、无 GPU 的模式下运行**；该模式下**无渲染世界、无 15703、无截图**（与 §3-7 一致）。
6. **五条观测在 headless 下全部成立（实测）**：位移、**计数 0→1**、胜利位 false→true、
   **跳跃 rise12 / fall12–16 / fall18**、**起跳前 Grounded=true 且落地后仍 true**。
7. **构建预算（headless 实测，取代 §4.4 数字）**：**冷 ≤302 s 实测 251 s / 暖 12 s（区间 16–19→12）/ 启动→端点 620 ms（窗口模式 2755 ms）**；
   预算上界仍取保守值：**冷 ≤600 s / 暖 ≤120 s / 单轮 ≤300 s / 端点等待轮询超时 30 s**。
   二进制 57.5 MiB、加载模块 10、依赖 crate 286（均为 headless 实测）。
8. **新增硬约束（防假一致性）**：**JSON-RPC batch 不是帧原子的**——含 24 个相同 `world.get_resources(CoinCounter)`
   的 batch 响应中**同时出现 coins:1 与 coins:2**（六次中一次）⇒ **禁止用 batch 做一致性快照**；
   一致性读取必须**逐调用**（或改用 `+watch` 流并接受其 `bounded(8)` 静默关流风险）。
9. **未验证项（明确不承诺）**：真·无桌面环境（本机始终有桌面会话；C4 证据是结构性的——winit 不在依赖图）、
   软件适配器（WARP/llvmpipe）、release headless、4 FPS 的确切机理、batch 非原子性的概率分布。
